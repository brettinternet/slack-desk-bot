# Slack thread activity indicator: agent-session research

## Decision

SlackDeskBot currently sends no interim thread message or typing indicator: `SlackAgent.createRequestStatus()` only counts tool use, and `deliverRequest()` posts the answer after execution (`src/slack.ts`). Commit `90a010f` removed the earlier “Queued…” / “Working…” reply and its updates. Slack does not offer an ordinary-bot typing signal through the APIs used here. The supported native option is an **agent-session loading state**: `agents.sessions.setStatus` with `processing` while work runs, followed by `active`. This displays Slack's “Working…” UX, **not** a typing animation or custom elapsed-time message. An app must be declared an agent to create sessions. [Agent sessions][sessions] · [Set status][set-status]

**Recommendation:** If an indicator inside a channel thread without another message is important, pilot agent sessions with a separate Slack app before changing the existing installation. If simple acknowledgement suffices, a temporary `:eyes:` reaction on the request is a smaller change using the existing `reactions:write` scope; it is not a thread typing indicator. Do not reintroduce a status reply solely to mimic typing unless an extra message is acceptable.

## Consequences of enabling the agent experience

| Area               | Finding and impact here                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App configuration  | The current `slack-app-manifest.yaml` enables the App Home Messages tab but has neither `agent_view` nor `assistant_view`. Declaring an agent enables agent sessions and adds `assistant:write`; the status method itself requires the existing `chat:write` scope and the app to be a channel member. `agent_view` requires an `agent_description`. Confirm workspace approval and installation/re-authorization requirements during rollout; no additional history scope is needed _for the status call_. [Sessions][sessions] · [Set status][set-status] · [Manifest][manifest] |
| User-facing UI     | Agent conversations appear in the ordinary Messages tab, rather than the older assistant Chat/History tabs. The app can also appear in Slack's agent discovery/navigation; owners/admins and members have display controls. This may make the bot more discoverable than its `SLACK_ALLOWED_USER_IDS` invocation policy suggests. Its existing allowlist remains an application-level check, not a Slack visibility control. [Announcement][announcement] · [Display agents][display]                                                                                              |
| Channel visibility | A session is scoped to a thread. All members of a channel can see its status and title and change its title, whether or not they initiated the request or are on this bot's allowlist. Avoid placing sensitive prompt text in a session title; a title is optional. [Sessions][sessions]                                                                                                                                                                                                                                                                                           |
| DMs                | Slack continues to deliver `message.im` events and allows direct replies or thread replies in the Agent messaging experience. This bot normally replies to unthreaded DMs without `thread_ts` (`src/slack.ts`); the status API requires the root `thread_ts` for thread-based sessions, including DM threads. Start with channel threads only. Adding native status to ordinary DMs would need a separate decision about creating/opening DM threads and preserving the bot's conversation routing. [Developing agents][developing] · [Set status][set-status]                     |
| State and errors   | Posting a reply does **not** end `processing`. Explicitly return to `active` after success, error, cancellation, and failed delivery; Slack otherwise times out the state after one hour. Account for concurrent/queued requests in the same thread so one turn cannot clear another's indicator. If status API calls fail, answers must still be delivered. The new API offers no custom progress text. [Sessions][sessions] · [Migration][migration]                                                                                                                             |
| Stop control       | Without an `agent_session_stopped` event subscription, Slack shows a non-interactive loading indicator. Subscribing shows a stop button, but then the bot must cancel the matching work and transition the session out of `processing`. This is optional for an initial indicator-only rollout. [Sessions][sessions]                                                                                                                                                                                                                                                               |
| Other users        | Slack says guests cannot use AI apps or agents. If this installation expects allowlisted guests to invoke the bot today, test that use case before switching. Admin app-approval policies may also apply. [Work with agents][work-with-agents]                                                                                                                                                                                                                                                                                                                                     |
| Reversibility      | Slack explicitly calls **`assistant_view` → `agent_view`** irreversible and says distributed apps need Marketplace review for that migration. This bot uses neither view; those statements do not establish whether adding and later removing `agent_view` for this bot is reversible. Test configuration rollback on a separate app rather than assuming it works. [Migration][migration]                                                                                                                                                                                         |

No source found establishes a separate charge specifically for `agent_view` or `agents.sessions.setStatus`. Slack's [end-user guide][work-with-agents] says agent use is available on all plans; that does not guarantee every AI development feature is available on every plan. Verify availability in the target workspace.

## Proposed pilot (not implemented)

1. Configure a separate app as an agent, preserving the existing Messages tab and bot event subscriptions. Confirm manifest acceptance, scopes, workspace approval, and what users see in navigation. Do not change the production app merely to test rollback.
2. In a channel mention thread, call `agents.sessions.setStatus({ channel_id, thread_ts: rootTs, status: "processing" })` on admission and set `active` after delivery in a cleanup path. Keep failures best-effort without hiding the answer. Verify whether the status is visible to channel members and whether setting it opens any UI unexpectedly.
3. Exercise an immediate response, a long run, backend failure, Slack delivery failure, cancellation, two queued requests in one thread, restarts, unauthorized users, ordinary DMs, and bot-initiated DMs. Check that no session remains `processing` and that normal DM/channel routing and allowlist behavior remain intact.
4. Decide separately whether to support status for threaded DMs or the native stop event. Only then update the existing app and document reauthorization and recovery steps.
